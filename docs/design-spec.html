Colony Command

Every Claude Code session becomes a small worker on a shared map. Projects are districts, directories are buildings, and the front porch is where agents come to find you. The map stays quiet while things are fine and gets loud only where your attention is needed.

Inspector

Click a bot

Bots on the porch need you. Red ones are stuck, yellow ones have a question. Packages on the review dock are finished work. Click the dock to mark them reviewed.

01Product vision

An operations console that looks like a colony sim, built so a two-second glance answers "does anything need me?"

Running ten to a hundred Claude Code sessions is an attention-routing problem. The agents are fast; the bottleneck is the human noticing that one of them stopped to ask a question forty minutes ago. Terminal tabs hide that. A dashboard table shows it but nobody keeps a table open all day.

Colony Command treats your sessions as a population living on one surface. Their state is shown through where they stand and how they move, so you read the whole fleet the way you read a room. The playful layer is there to make the tool pleasant to keep open, and every bit of it must carry real information.

Visuals never lie

Every animation maps to a real signal. A state change shows on the bot's badge within one second, even if the bot is still walking to its new spot.

Calm until it isn't

Healthy work moves slowly and quietly. Motion, color saturation, and sound are reserved for things that need you. This is the attention budget.

Space carries meaning

Districts are projects, buildings are directories, the porch is you. Bots keep stable home spots so your spatial memory does half the work.

Act where you look

Approve a permission, answer a question, interrupt, or kill from the map. Opening a terminal is the fallback, not the main path.

Three to three hundred

Level of detail collapses bots into dots and districts into heat at scale, while the porch always shows every agent that needs you.

02User experience flows

The eight flows that matter, in the order a typical day hits them.

A. Morning open

  1. App launches with Windows; the daemon was already running and has been recording overnight.
  2. The camera opens on the full colony. A small "while you were away" scroll on the porch lists what changed: 3 finished, 1 crashed, 2 waiting since 02:14.
  3. Press R to play a 20-second time-lapse of the night, or Esc to dismiss.

B. Glance and triage

  1. Look at the porch. Red bots stand at the front, yellow behind them, ordered by severity then wait time.
  2. Press Space to jump to the first one. The camera eases to it and the inspector opens on the question or error.
  3. Resolve it (approve, answer, or dismiss); the bot visibly walks back to its district and starts working. Space again for the next.

C. Approve a permission from the map

  1. A bot hits a permission prompt for Bash(npm run migrate). Its hook holds the request and tells the daemon.
  2. The bot walks to the porch holding a yellow card showing the command. Hover shows the full command and cwd.
  3. Click Allow once, Allow always for this project, or Deny with note. The hook returns the decision; Claude continues.

D. Answer a question

  1. Agent ends its turn with a question. The daemon classifies the last message as a question (heuristics, optional Haiku classifier).
  2. Bot holds up a "?" card and periodically raises its hand. Inspector shows the question, the last three assistant messages, and a reply box.
  3. Type a reply. It is sent into the session's PTY (for sessions Colony launched) or copied with a "focus terminal" button (for adopted external sessions).

E. Review finished work

  1. A bot finishes a turn with no question pending. It celebrates, raises a blue flag, and carries a package to the review dock.
  2. Click the package: summary of the final message, files changed (git diff stat), tests run, tokens spent.
  3. Mark reviewed (bot goes idle), send follow-up (bot goes back to work), or open the diff in your editor.

F. Spawn a new bot

  1. Drag from the "hatchery" button onto a district, or press N and pick a project.
  2. Choose host (Windows or a WSL distro), model, permission mode, and type the objective.
  3. Colony launches claude in a PTY it owns; a bot hatches in the district and walks to its first building.

G. Dive into a workspace

  1. Double-click a bot. The camera zooms into its district; buildings expand into the directories it has touched, lit by recency.
  2. Subagents are visible at their own buildings with tethers back to the parent. A terminal pane slides up with the live session.

H. Handle a crash

  1. Process exits without a SessionEnd event. The bot keels over in place, a red marker appears, and it is added to the porch as a ghost.
  2. Inspector offers Resume (runs claude --resume <id> in a new Colony PTY), View last output, or Archive.

Each mechanic is a productivity feature first. The "game" column is how it looks; the "job" column is why it exists.

Rules that keep it honest

  • Truth latency under one second. The status ring and overhead icon switch immediately. Walking to the new place can take a few seconds; the badge does not wait for the walk.
  • Stable homes. Each bot gets a home tile seeded from its session id. Same bot, same place, every day.
  • No idle fidgeting that resembles distress. Idle animations never use arm-waving or fast motion, so they cannot be mistaken for a blocked bot.
  • Color is never the only channel. Each state also has a distinct silhouette, icon, and motion pattern, so it works for color-blind users and at small sizes.

Components

colony-hook (per platform, static binary)

Registered for every Claude Code hook event in user-level settings.json. Reads the hook JSON from stdin, adds its parent process chain (so the daemon can map session_id to a PID), and forwards it. It must return in under 50 ms for observe-only events. If the daemon is down it appends to a spool file and exits 0, so Claude Code is never slowed or broken by Colony. For PreToolUse it can optionally wait for a decision (see Control below).

// ~/.claude/settings.json (user level), installed by Colony with a diff preview
{
  "hooks": {
    "SessionStart":     [{ "hooks": [{ "type": "command", "command": "colony-hook" }] }],
    "UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "colony-hook" }] }],
    "PreToolUse":       [{ "matcher": "*", "hooks": [{ "type": "command", "command": "colony-hook --gate", "timeout": 600 }] }],
    "PostToolUse":      [{ "matcher": "*", "hooks": [{ "type": "command", "command": "colony-hook" }] }],
    "Notification":     [{ "hooks": [{ "type": "command", "command": "colony-hook" }] }],
    "Stop":             [{ "hooks": [{ "type": "command", "command": "colony-hook" }] }],
    "SubagentStop":     [{ "hooks": [{ "type": "command", "command": "colony-hook" }] }],
    "PreCompact":       [{ "hooks": [{ "type": "command", "command": "colony-hook" }] }],
    "SessionEnd":       [{ "hooks": [{ "type": "command", "command": "colony-hook" }] }]
  }
}

colony-probe (inside each WSL distro)

The daemon starts it with wsl.exe -d <distro> -- ~/.colony/bin/colony-probe --stdio and talks to it over stdin/stdout. That avoids WSL networking entirely: NAT versus mirrored mode, firewall rules, and changing host IPs stop mattering. The probe:

  • listens on ~/.colony/hook.sock for colony-hook events from Linux sessions;
  • tails ~/.claude/projects/**/*.jsonl with inotify (watching \\wsl$ from Windows is unreliable and slow);
  • scans /proc every 2 s for claude processes, their cwd, parent tree, and CPU time;
  • hosts PTYs for sessions Colony launches inside WSL.

colonyd (Windows daemon)

Runs at login as a per-user background process (not a Windows service; it needs the user's profile and console). Owns the event log, all derived state, the PTY host for Windows sessions, and the local API. Keeps working with the UI closed, so OS notifications still fire and history is never lost.

Pause, defined honestly. You cannot freeze a model mid-response. Colony's pause means "finish the current tool call, then hold before the next one". The gate hook simply does not return until you resume. It works for every session that has the hook installed, including ones you started yourself.
The gate hook delays every tool call slightly. By default it only blocks for tools the session would have prompted for anyway, plus any session that is paused. Everything else returns immediately with no decision, leaving Claude Code's own permission rules in charge. Check the hook input and output fields against the Claude Code version you have installed; the hook schema has changed between releases.

Layers, back to front

  1. Terrain: tile map, district plots, buildings, weather. Redrawn only on layout change, cached to a texture.
  2. Actors: bots, subagents, packages, tethers, particles. Sorted by y.
  3. World labels: district names, building names on zoom, bot nameplates on hover. Rendered as bitmap text for speed.

Family-tree view

Press T on a bot and the world fades back while its lineage lays out as a tidy tree: parent at top, subagents below with state rings, returned ones dimmed with a check, blocked ones pulsing. 08Data model

Event-sourced. The log is the source of truth; everything else is a projection that can be rebuilt.

type HostId = `win` | `wsl:${string}`;           // "wsl:Ubuntu-24.04"

Rules

  • Hooks and transcripts overlap on purpose. Hooks are fast and structured; transcripts survive when hooks are not installed and fill in token usage. Dedupe on tool_use_id and transcript uuid.
  • Ordering is per-session by source timestamp; cross-session ordering does not matter.
  • Subagent attribution: prefer subagent transcript files where Claude Code writes them; otherwise attribute tool events to the most recent open Task on that session. Mark heuristic attributions so the UI can show a dashed tether.
  • Snapshot plus deltas to the UI: on connect, a full snapshot at seq; after that, reducer outputs only. Reconnect sends since=seq.

10Animation system

Procedural rigs rather than hand-drawn frames, so a handful of parts can express many states and scale to hundreds of bots.

Bot rig

  • Body: a soft blob in the project color with squash-and-stretch driven by velocity and landing.
  • Eyes: the main emotion channel. Pupil direction follows the target; "looks at you" means pupils down toward the camera. Lids lower when idle, widen when blocked.
  • Arms: two-segment lines with IK to hand targets (prop, raised, waving).
  • Prop slot: book, hammer, card, flag, package, telescope.
  • Status ring: ground ellipse in the state color. The single most reliable state signal at every zoom.
  • Overhead slot: one icon at a time, chosen by priority (crash > blocked > permission > question > flag > tool glyph).

Animation graph

Each state maps to a clip set: enter, loop, and exit. Loops have parameters fed from the mood layer: urgency raises hand-raise frequency, pace speed, and icon pulse rate; valence tilts posture. Transitions cross-fade over 150 ms; a state change always plays the exit and enter beats, even if short, so changes catch the eye once.

Tethers

Verlet ropes with 8 segments between parent and subagent, slack when close, taut when far. Color is the project color; dashed when attribution is heuristic; red when the subagent is blocked. When a worker returns, the rope reels in.

  • 500 bots at 60 fps on integrated graphics: one sprite batch for bodies, one for rings, particle pool capped at 2k.
  • Sim tick at 20 Hz with render interpolation. Pathfinding on a coarse grid, cached per district.
  • When the window is unfocused, render drops to 10 fps; when minimized, render stops and the daemon carries on.
  • prefers-reduced-motion: no particles, no bounces; states shown with rings and icons, and moves become fades.

Sound (off by default)

One soft chime when a bot reaches the porch, a lower tone for red. Nothing for healthy work. Volume follows urgency.

12MVP definition

The smallest version that already cuts human latency: see every session on Windows and WSL, know which ones need you, and act on the common cases.

In

  • colonyd + colony-hook (Windows), colony-probe + colony-hook (WSL)
  • One-click hook install with diff preview and uninstall
  • Session discovery from hooks, transcripts, and processes
  • States: working, needs input, awaiting reply, blocked, ready to review, idle, crashed
  • Subagent spawn and return, with tethers
  • Map with districts, porch, dock; normal and far LOD
  • Inspector: objective, todos, tokens, current tool, last messages
  • Launch new sessions in Colony PTYs; send, interrupt, kill for those
  • Kill for any session; "focus terminal" for adopted ones
  • OS notification when an item has waited past its patience budget

Out (for now)

  • Gate hook approvals and pause (V1.1, needs careful testing)
  • Buildings per directory (districts only in MVP)
  • Weather, day cycle, sound
  • Time-lapse replay
  • Squads and broadcast
  • Headless SDK fleets
  • Phone companion
  • Haiku classifier (rules only)

Acceptance criteria

  • A session started in any Windows terminal or WSL shell appears on the map within 2 s of its first prompt.
  • A permission prompt shows the bot on the porch within 1 s.
  • A killed terminal shows as crashed within 5 s.
  • With the daemon stopped, Claude Code runs with no visible delay and no errors.
  • 50 simulated sessions render at 60 fps; daemon idles under 1% CPU and 80 MB RAM.

First tasks, in order

  1. Write a throwaway hook script that appends raw stdin to a file, install it for every event, and run real sessions on both hosts. This answers most open questions about the schema.
  2. Define colony-core types and the reducer for the lifecycle machine; test it against those captured logs.
  3. Build the synth generator early. It drives the renderer before the real pipeline is finished, and it stays the load test.
  4. Build the porch before the districts. It is the feature that pays for the whole app.
